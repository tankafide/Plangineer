# Build Plangineer on one TypeScript toolchain, guarded by fast checks

Plangineer should be a single-language TypeScript monorepo on one runtime, Node 24: a React 19 + Vite 8 client-rendered SPA, a Node monolith control plane (Hono + oRPC + Zod over Postgres/Drizzle, with run dispatch in a Postgres `runs` table), and a local runner shipped as an npm package. It is open source and self-hosted, one deployment per team, so the whole server ships as one Docker image plus Postgres. The runner, the self-hosted deployment and development of Plangineer itself must work the same on Windows, macOS and Linux, and because the project is built on Windows, the stack has to guard against assumptions that only hold on one machine. The product spec makes this the natural shape. Agents run on runners, not in the control plane, so the backend is I/O-bound dispatch, event storage and webhooks, and one language lets the same Zod schemas serve web, API, runner and a later Expo app. The runner supports Claude Code first and Codex second; Cursor is out of scope for this version. The spec's biggest uncertainties are not framework choices but runner behaviour (Windows process-tree kill, CLI output drift) and vendor terms for subscription logins. For delegated development, the decisive investment is a single deterministic `pnpm verify` gate enforced identically in agent hooks, git hooks and CI, a one-command dev environment agents can run and inspect, and, once agents write most of the code, protections that stop them weakening tests. Several claims in the [research notes](../research/tech-stack/) conflicted or rested on one secondary source; package versions were rechecked against the npm registry on 6 October 2026, and the remaining open items are listed below with a resolution for each. Short decisions for agents live in [stack decisions](stack-decisions.md); this report is the reasoning behind them ([product spec](../product/mvp.md)).

**Update, Oct 9, 2026.** Plangineer now ships first as an Electron desktop app, as the [desktop app plan](../plans/2026-10-08-desktop-app.md) decides. Three rows below change as a result. Deployment: the desktop app runs the server bundles and bundled Postgres binaries on the engineer's computer, and the Docker image plus Postgres becomes the later team server. Mobile path: a phone app connects to the engineer's desktop, which keeps running the CLIs, and how it reaches that desktop is an open decision in the product spec. Local runner: the desktop app runs the runner on Electron's Node 24, and npm stays the install path for a second machine. The rest of this report stands.

## A single-language monolith fits a product whose agents run elsewhere

The control plane described in the spec queues one job per run, receives streamed events, handles Git host webhooks and stores plans, findings and run history; the agent work itself happens on a runner. That framing removes the usual reasons to reach for Go or Python. The two reference background-agent projects show the cost of splitting languages: Open-Inspect pairs a TypeScript control plane with Python sandboxes, and Open SWE pairs a Python backend with a TypeScript UI ([Open-Inspect](https://github.com/ColeMurray/background-agents); [Open SWE](https://github.com/langchain-ai/open-swe)). Neither is a drop-in base, since Open-Inspect is built on Cloudflare Durable Objects and Open SWE on LangGraph and its own agent loop rather than the vendor CLIs. Everything Plangineer defines (job messages, RunEvents, API contracts) is a Zod schema in one `packages/contracts` workspace consumed by web, API, runner and later mobile. Running the runner on Node too means one runtime across the repo, so shared packages need no runtime-neutrality discipline. The caveat is evidence quality: the notes found no 2026 benchmark of agent code quality by language, and one study they cite found Python-dominant commits had a higher first-try commit rate than TypeScript-dominant ones (48.4% vs 41.7% for Opus) ([arXiv 2602.17955](https://arxiv.org/abs/2602.17955v1)). The case for TypeScript here is shared types and compiler feedback across web, API and runner, not a proven agent-success advantage.

On the web side, an authenticated, highly interactive app with no SEO surface gains nothing from server rendering. React is used by 83.6% of State of JS 2025 respondents while Next.js drew the most polarised commentary ([InfoQ](https://www.infoq.com/news/2026/03/state-of-js-survey-2025)), and one summary of AI-coding benchmarks puts success on Next.js-specific tasks near 42% and multi-step full-stack integrations near 25% ([Addy Osmani](https://addyosmani.com/blog/how-good-is-ai-at-coding-react-really/)). So the recommendation is React 19 + TypeScript on Vite 8 (released 12 March 2026 with Rolldown as the single bundler ([Vite 8](https://vite.dev/blog/announcing-vite8))), with TanStack Router for type-safe file-based routing. Styling is Tailwind v4 plus shadcn/ui, the stack AI tools converge on, with copy-in components agents can read and edit ([React AI stack 2026](https://builder-proxy.humanx.co/blog/react-ai-stack-2026)). The spec's phone-width requirement is met by a one-column-first layout using shadcn Drawer/Sheet for bottom-sheet findings, and button-driven reorder alongside dnd-kit. The plan is typed JSON rendered as cards, not a rich-text document: use the `diff` package for per-field revision diffs, react-diff-view for code diffs with inline-finding widgets ([npm](https://npmjs.com/package/react-diff-view)), and CodeMirror 6 for raw context-file editing. Server state goes through TanStack Query; run timelines arrive over fetch-based SSE with `Last-Event-ID` resume so bearer tokens work and a React Native reader can reuse the logic ([WebSocket.org](https://websocket.org/comparisons/sse/)). A backgrounded phone browser drops the stream, so resume-by-id plus notifications is the contract.

Mobile follows the spec's "responsive web first" decision. iOS web push only works for Home Screen-installed PWAs and has no silent push ([MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)), so if reliable "decision needed" alerts matter, Expo (SDK 56 on React Native 0.85 ([Expo](https://expo.dev/sdk/56))) is the upgrade, reusing `contracts`, the API client, query hooks, the SSE reducer and domain functions such as coverage, staleness and amendment-level computation. The repo layout (`packages/contracts`, `api-client`, `domain`, `apps/web`, later `apps/mobile`) should be set up now. The notes' "40-60% of non-view code carries over" figure is the author's own estimate and should not be relied on.

## The control plane is a Postgres-centred TypeScript service

Hono with oRPC is the API recommendation because oRPC emits OpenAPI 3.1 natively while tRPC cannot, and OpenAPI matters for a possibly native mobile app, runner and webhook consumers, and agents calling plain HTTP ([PkgPulse](https://www.pkgpulse.com/guides/orpc-vs-trpc-vs-hono-rpc-type-safe-apis-2026); [Supastarter](https://supastarter.dev/blog/hono-vs-trpc-vs-orpc-api-comparison)). oRPC announced v1 in December 2025 ([InfoQ](https://infoq.com/news/2025/12/orpc-v1-typesafe/)); npm shows 1.15.4 as latest with 2.0 in beta, so pin v1 and budget one major upgrade. The evidence for its SSE `eventIterator` behaviour and React Query integration is promotional aggregators, so the fallback is Hono with `@hono/zod-openapi`, which gives the same OpenAPI benefit with a bigger ecosystem. The runner-to-control-plane protocol is a separate, small Zod schema in the same package, carried over a single outbound WebSocket (job push, cancel, heartbeats up, events up), which is what Open-Inspect's bridge also does ([Open-Inspect](https://github.com/ColeMurray/background-agents)). Codex's own WebSocket transport is explicitly experimental, so the link should be Plangineer's own.

For state, the spec's "plan revisions are never edited in place" maps to immutable revision rows with JSONB bodies, findings as their own table because triage queries filter on their fields, and an append-only `run_events` table with a per-run sequence number. SSE is then just a tail of that table, so reconnect, replay and the run timeline come for free, and the stream is never the source of truth. Drizzle gives schema-as-TypeScript with built-in Zod validators, and Better Auth ships a Drizzle adapter ([Better Auth releases](https://newreleases.io/project/npm/better-auth/release/1.6.23)). Pin Drizzle 0.45.x: v1 is still at a release candidate (`1.0.0-rc.5`), and agents know the 0.x API better. Use `drizzle-kit push` while the schema churns and switch to generated migrations before any data the team cares about exists; keep seed scripts so any database can be recreated.

Run dispatch needs no queue library. The `runs` table already holds everything a queue would: status, lease owner, lease expiry, heartbeat time and a cancel flag. When a runner connects or finishes a job, the control plane claims the next eligible run with `SELECT … FOR UPDATE SKIP LOCKED` and pushes it over that runner's WebSocket; the runner heartbeats, and a periodic sweep marks a run lost when its lease expires. Per-engineer and per-repository concurrency limits (needed because parallel tasks share one subscription plan) belong in the claim query. Webhooks are written to a table keyed on delivery id and processed from there. Adding pg-boss would give a second source of truth for the same state, so it is added only if a real need for cron schedules or retry policies appears. Trigger.dev (Apache 2.0, no-timeout tasks, checkpointing) is the revisit option only if the control plane itself must execute long agent loops ([Trigger.dev](https://github.com/triggerdotdev/trigger.dev)); Temporal's cluster ops cost is not justified for a process that runs in someone else's shell.

Auth and Git host integration follow from self-hosting. One deployment serves one team, so there is no tenancy: Better Auth (self-hosted, Drizzle adapter, GitHub sign-in, Expo package) keeps users in the same Postgres, and each user carries an admin or member role instead of an organization membership. Better Auth has had a real security advisory (CVE-2026-53515, an `@better-auth/sso` registration flaw fixed in 1.6.11 ([GitLab advisory](https://advisories.gitlab.com/npm/@better-auth/sso/CVE-2026-53515/))), so skip the SSO plugin, pin versions and watch advisories. Authorization is row-level policy functions plus foreign keys, including "approver is not the author", with no external authz engine. GitHub should be a GitHub App, not an OAuth App: fine-grained permissions, one-hour installation tokens, and centralised webhooks ([GitHub docs](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps); [Nango](https://nango.dev/blog/github-app-vs-github-oauth)). Because every team self-hosts, each deployment registers its own app; GitHub's app manifest flow lets the setup screen create it in one click with the right permissions and webhook URL. Use Octokit, verify `X-Hub-Signature-256`, dedupe on `X-GitHub-Delivery`, acknowledge fast and process from the table. The notes' suggested permissions and events (Contents, Pull requests, Checks, Actions; push, pull_request, check_run, workflow_run, deployment_status) are unverified judgment and should be checked against current docs.

Deployment is one Docker image plus Postgres, shipped with a Docker Compose file that also runs MinIO, so a team can self-host with one command and the same file is the local dev environment. Long-lived SSE and runner WebSockets rule out serverless functions. Evidence files go to any S3-compatible store through the S3 SDK with presigned PUTs so runners upload directly; MinIO covers local and small deployments, and R2 or S3 covers larger ones. Reverse-proxy idle timeouts for long SSE connections vary by host, so the SSE stream sends a heartbeat comment every 15 to 30 seconds.

## The runner is the riskiest component, and subscription terms constrain its design

The local runner is a TypeScript package on Node 24, published to npm and started with `npx plangineer-runner`. Engineers who use Claude Code or Codex already have Node, so npm handles installation and updates, and there is nothing to sign: no code-signing certificate, no Windows SmartScreen reputation to build and no self-update swap. It also keeps the repo on one runtime. The notes' original choice, `bun build --compile`, was rejected for that reason and because Bun has had recent process-spawn regressions; one in Bun 1.3.13 broke Claude Code itself under WSL2 ([issue](https://claudeissues.com/issue/52455-bug-enoexec-error-when-running-claude-code-on-wsl2-bun-v1-3-13-regression)). If a standalone binary is ever needed, Node 25.5+ builds one directly with `--build-sea` ([Node Weekly](https://nodeweekly.com/issues/609)).

The adapter interface is `spawn(job) -> AsyncIterable<RunEvent>`, with one native adapter per CLI, Claude Code first. Claude Code runs as `claude -p --output-format stream-json --verbose --include-partial-messages` with an explicit `--permission-mode` and `--allowedTools`, `--json-schema` for validated findings, and feature detection through `system/init.capabilities`; its stream uniquely carries cost, retry/rate-limit categories and permission denials, which map straight onto the spec's cost display and "plan limit reached" state ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). `--bare` is unusable locally because it skips OAuth login and repo skills. Codex follows once the workflow runs end to end on Claude Code, through one integration mode, `codex exec --json` with `--output-schema` for structured roles ([Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode)). `codex app-server` adds approvals, interrupt and resume, but the spec's implementer never stops to ask, so a second Codex mode is not worth building. Neither output format carries a documented stability guarantee beyond Claude's capabilities array, and Codex has already deprecated `--full-auto`, so each run records the CLI version and a recorded-run conformance suite runs against latest versions. ACP covers both agents ([ACP registry](https://agentclientprotocol.com/registry/index)) but its remote transport is unfinished and it lacks first-class cost or structured-output equivalents, so it is a later generic adapter (and the likely route to Cursor) rather than the foundation.

Vendor terms favour spawning the engineer's own installed binary, and open-source self-hosting keeps Plangineer out of the login path. Anthropic does not permit third-party developers to offer claude.ai login or its rate limits in products, including those built on the Agent SDK, and forbids collecting, storing or relaying Claude credentials, while an end user signing in to the unmodified Claude Code binary is allowed ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [legal](https://code.claude.com/docs/en/legal-and-compliance)). The runner therefore never reads or ships logins, and does not use the vendor SDKs as its primary path for subscription use. OpenAI's Sign in with ChatGPT program explicitly allows open-source and locally hosted apps to use a person's ChatGPT plan ([OpenAI](https://developers.openai.com/siwc/token-sharing-open-source)). Two Claude questions remain open: whether a third-party runner spawning the user's `claude` counts as "third-party app usage" under plan limits, and hosted Claude Code on a subscription. Both need Anthropic's confirmation, and the spec's setting-per-role and no-silent-API-fallback rules already contain the blast radius ([Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). Anyone who runs a deployment as a service for other companies takes on the vendors' commercial terms themselves.

Operationally, each run gets a worktree under a runner-owned directory (a bare clone plus `git worktree add`, detached for read-only roles), never the engineer's own checkout. Supervision uses idle and wall-clock timeouts and a platform-specific stop (see the cross-platform section below), a per-vendor concurrency lane that pauses on rate-limit events, and a bounded on-disk event buffer replayed after reconnect. Repo hooks and `.mcp.json` execute as code, so the run record should list which loaded. These worktree and supervision details are standard practice from the notes' inferences, not cited findings. Windows is the notable gap: the notes verified nothing about spawning the CLIs, process-tree kill or long worktree paths there. For hosted runners, start with one-shot GitHub Actions jobs running the same package with API keys and `dontAsk`-style permissions, matching the spec's "CI runners first"; put a `SandboxProvider` interface in front so E2B or Daytona can replace it later. Isolation and persistence claims about sandbox vendors come from a Fly.io-authored comparison and are biased ([Fly.io](https://fly.io/learn/agent-sandbox-providers/)).

## Fast deterministic checks are the real agent harness, and the guardrails come in stages

The tooling notes make the central argument well: agents iterate on whatever deterministic feedback is quick, and Anthropic's own guidance is to give Claude a check it can run and to enforce it with a Stop hook ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The gate is one `pnpm verify`, orchestrated by Turborepo over a pnpm workspace: format check, Oxlint with tsgolint type-aware rules and `--type-check`, `tsc`, dependency-cruiser, Knip, `vitest run`. It is identical in four places. A PostToolUse hook on `Edit|Write` runs the fast variant (format plus lint on the file); a Stop hook runs the full gate (honouring `stop_hook_active`, since Stop hooks are overridden after eight consecutive blocks ([hooks guide](https://code.claude.com/docs/en/hooks-guide))); lefthook runs it pre-push; and one required GitHub Actions job runs it as the authoritative check on `windows-latest`, `macos-latest` and `ubuntu-latest`, because agents use `--no-verify` and because a check that passes only on the machine it was written on proves little. Standard GitHub-hosted runners, macOS included, are free for public repositories. Because Plangineer also runs Codex, and the notes researched only Claude hooks, the git hook and CI layers are the agent-agnostic backstop.

Every hook and repo script is a Node script (`node scripts/<name>.mjs`), never a bash or PowerShell script. On Windows, Claude Code runs hook commands under Git Bash or cmd depending on what is on `PATH`, while the model is told its shell is PowerShell ([issue](https://claudeissues.com/issue/59225-bug-windows-model-is-told-shell-powershell-while-hooks-execute-under-bash-cross)); invoking `node` directly behaves the same on Windows, macOS and Linux ([cross-platform hooks](https://claudefa.st/blog/tools/hooks/cross-platform-hooks)).

The guardrails beyond the gate are staged, so none is built before it has something to protect:

| Stage | Adds | When |
| --- | --- | --- |
| Day one | `pnpm verify`, PostToolUse and Stop hooks, lefthook pre-push, the required CI job | Before the first feature |
| Agents write most of the code | PreToolUse guards against `--no-verify`, force-push and edits to lint, test and CI configuration; protected test paths; the CI diff-guard; acceptance-criterion ids in test titles | As soon as agent-written changes outnumber hand-written ones, likely early in Phase 1 |
| Pure logic has settled | Stryker, diff-scoped, on the `domain` package only; fast-check property tests on event parsing | Once triage, staleness, amendment-level and deviation-matching logic stop churning |

On linting, the notes agree on the facts. TypeScript 7.0 went GA on 8 July 2026, about 10x faster than 6.0, but without a stable programmatic API ([TypeScript blog](https://devblogs.microsoft.com/typescript/?p=5246)); typescript-eslint 8.71 still peer-depends on TypeScript `<6.1.0` ([DEV Community](https://dev.to/the-modern-web/why-angular-vue-and-eslint-cant-upgrade-to-typescript-70-yet-and-why-ts-71-changes-441g)). tsgolint runs on the TS 7 compiler, covers 59 of typescript-eslint's 61 type-aware rules, and is reported 12-18x faster ([Oxc blog](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). So the recommendation is Oxlint plus tsgolint on TS 7, with Oxfmt for formatting (still pre-1.0 at 0.72, but 100% Prettier JS/TS conformant, so a swap back is a one-command change ([Oxc](https://oxc.rs/blog/2026-02-24-oxfmt-beta))). Because Oxlint's JS plugin API was only confirmed as alpha in March 2026 ([Oxc](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha)), the rule set relies on native rules (`no-restricted-imports`, `import/no-cycle`, `max-lines`) and treats custom JS-plugin rules, such as ones with remediation text, as optional. This follows Fowler's point that lint messages telling the agent how to fix a violation are effective feedforward ([Martin Fowler](https://martinfowler.com/articles/harness-engineering.html)).

Architecture boundaries are enforced in layers: pnpm's strict isolation makes undeclared imports fail at resolve time; dependency-cruiser on the resolved import graph is the authoritative layer gate (domain imports nothing but `contracts` and Zod; web never imports API internals; nothing imports from `apps/*`), with the rule `comment` field written as a fix instruction; Oxlint gives instant in-edit feedback; Knip catches dead code and unlisted dependencies. Nx tags are rejected because the same enforcement is available without a build-system migration. The notes' thresholds (300 lines per file, 50 per function) are the author's judgment.

For tests, Vitest 5 (5.0.3 on npm; announced 3 September 2026, requiring Node 22.12+ and Vite 6.4+) with root `projects` fits a monorepo, and its `agent` reporter (added in 4.1) cuts output for agent runs ([Vitest 4.1](https://vitest.dev/blog/vitest-4-1); [Vitest blog](https://vitest.dev/blog)). Vitest 5 also fails unawaited async assertions, removing a classic agent false-pass. Integration tests use real Postgres: migrate once into a template database and `CREATE DATABASE ... TEMPLATE` per worker, with per-test rollback via `aroundEach` for ordinary tests and per-file databases for dispatch, `LISTEN/NOTIFY` and `SKIP LOCKED` tests, plus one CI job migrating from empty ([qaskills](https://qaskills.sh/blog/testcontainers-postgres-per-test-database)). PGlite is single-connection, so it cannot test concurrent dispatch and is at most an optional fast lane ([Electric](https://electric.ax/blog/2026/06/25/pglite-reaches-10-million-weekly-downloads.md)). Runner tests use a `fake-agent` executable driven by scenario files (partial lines, hangs, ignored SIGTERM) plus golden JSONL fixtures per CLI version. GitHub is mocked with MSW over a typed in-memory fake, and webhooks replay signed fixtures. Contracts need no Pact while web and API deploy together: shared Zod schemas, a committed generated OpenAPI file with a no-diff CI check, and responses validated against schemas ([Speakeasy](https://www.speakeasy.com/blog/pact-vs-openapi)). Playwright Test runs a `desktop-chromium` and a `phone` project over the same specs, with role locators, trace on failure and blob-report sharding ([Playwright sharding](https://playwright.dev/docs/test-sharding)), while the product's Verify stage uses `playwright-cli`, which one benchmark measured at about 27,000 tokens against 114,000 for MCP ([Bug0](https://bug0.com/blog/playwright-cli-vs-playwright-mcp-ai-browser-testing-2026)). Keep e2e thin (roughly 10-20 journeys, from the notes' estimate) and run it against the fake agent, never a real model.

Since agents write the tests, the second-stage guardrails matter as much as the runner. Documented agent behaviours include weakening matchers, stripping assertions, skipping tests and suppressing type or lint errors ([DEV: 327 PR analysis](https://dev.to/moonrunnerkc/ai-agents-cheat-on-pull-requests-i-mined-327-of-them-to-prove-it-43ij); [DEV: tests an agent is allowed to edit](https://dev.to/penloom_studio_829b7817d3/your-ai-agent-will-pass-any-test-its-allowed-to-edit-51fo)), though both are blog-level evidence about frequency. The countermeasures fit Plangineer's own plan model. Protected paths (existing assertions, snapshots, test, coverage and CI configuration) block edits unless a run is tagged as an approved test change, and modified or deleted tests surface as a mandatory finding like the spec's deviation mechanism. A CI diff-guard, run outside the agent's reach, flags removed `expect` calls, new `.skip/.only`, loosened matchers, new suppression comments and lowered thresholds. Acceptance-criterion ids appear in test titles (`AC-3: ...`) and CI checks that each plan row has a referencing test. Stryker (10.0 on npm; its Vitest runner accepts `vitest >=2`) measures whether agent-written tests detect behaviour changes, which line coverage does not: one practitioner found a 38% mutation score on a feature whose coverage looked fine ([alexop.dev](https://alexop.dev/posts/mutation-testing-ai-agents-vitest-browser-mode/)). Its TypeScript checker uses the TypeScript programmatic API that TS 7 lacks, so run it without the checker or against `@typescript/typescript6`. Stryker is reportedly incompatible with Vitest Browser Mode, so mutate only node projects. The Verify stage, which writes checks from the plan without seeing the implementation, is the holdout layer. Model-judgment code (review quality, confirm step) is tested through a small seeded-defect eval set run nightly under a cost cap, not in the blocking pipeline.

## Windows, macOS and Linux are equal targets

Plangineer is developed on Windows and used on all three systems, so the risk is not that one platform is unsupported but that one machine's habits leak into the code. Each difference that bites Node tools has a standard answer, and the stack takes it everywhere rather than branching per platform:

| Difference | What goes wrong | Rule |
| --- | --- | --- |
| Shells | Bash scripts fail on Windows; PowerShell scripts fail elsewhere; Claude Code hooks run under Git Bash or cmd on Windows | Every hook, repo script and `package.json` script is a Node script (`node scripts/<name>.mjs`). No inline env assignments (`FOO=1 cmd`), `rm -rf`, `cp` or `&&` chains that assume a shell |
| Paths | Hard-coded `/` or `\`, drive letters, `~`, and `file://` URLs built by hand | Build paths with `node:path`, convert with `fileURLToPath`; keep runner data in the platform's user data directory via `env-paths`; tests compare normalised paths |
| Line endings | Git's `core.autocrlf` rewrites files differently per machine, which churns diffs and breaks snapshot and fixture tests. Git for Windows installs default to `core.autocrlf=true` | A committed `.gitattributes` with `* text=auto eol=lf`; Oxfmt writes LF; stream parsers accept CRLF from CLIs |
| Case sensitivity | Windows and macOS ignore filename case, Linux does not, so a wrong-case import passes locally and fails in CI | Kebab-case filenames; `forceConsistentCasingInFileNames`; the Linux CI leg catches the rest |
| Spawning CLIs | On Windows, npm-installed CLIs such as `codex` are `.cmd` shims that `child_process.spawn` refuses without a shell, and `shell: true` mangles arguments | Spawn every CLI through execa (cross-spawn underneath), never with `shell: true` |
| Stopping processes | Windows has no POSIX signals or process groups, so SIGINT and `kill(-pid)` do nothing useful | On macOS and Linux, start the CLI in its own process group and signal the group (SIGINT, then SIGTERM, then SIGKILL); on Windows, `taskkill /pid <pid> /T /F` |
| Long paths and locks | Windows' 260-character path limit breaks deep worktrees; open file handles block deleting a worktree | `core.longpaths=true` on runner-owned clones, a short runner root, and worktree removal that retries |
| Symlinks | Creating them on Windows needs Developer Mode or admin, and Git checks them out as plain files by default | Never rely on symlinks; skill mirroring copies files |
| Local services | Native Postgres installs differ per system | Postgres and MinIO run through Docker Compose (Docker Desktop on Windows and macOS) |

The CI matrix is what keeps these rules honest: `pnpm verify` and the runner's tests run on Windows, macOS and Linux for every change, and Playwright e2e runs on Linux only, since the browser app does not depend on the server's platform.

## Agents need a dev loop they can run and inspect on their own

The gate tells an agent whether code is correct; the dev loop lets it see what the code does. Four pieces matter more for agent productivity than any library choice:

- **One command to start everything.** `pnpm dev` starts Postgres and MinIO through Docker Compose, then the API, the web app and the fake agent, with seed data loaded. `pnpm db:reset` drops, migrates and reseeds. Seed data covers every screen, including a feature in each workflow stage, so an agent can open any view without building state by hand.
- **A way to check the UI.** A `ui-check` rule skill tells the agent to run the app and drive it with `playwright-cli`, taking screenshots at desktop and phone widths (375 px), and to look at them before calling UI work done. The spec's phone-width requirement is otherwise unchecked until someone opens a phone.
- **Fail-loud config.** Each app parses its environment with a Zod schema at startup and exits with the list of missing or invalid variables. A committed `.env.example` holds every variable with a safe local value.
- **Readable logs.** The API and runner log structured JSON with pino to stdout and to `logs/<app>.log`, so an agent can read what happened after a failed request or run without reproducing it.

AGENTS.md should stay short and operational. Anthropic advises keeping only lines whose removal would cause mistakes ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)); one secondary summary reports that human-written context files cut median time by 28.64% while LLM-generated ones lowered success by about 3% and raised cost over 20% ([arXiv 2601.20404](https://arxiv.org/pdf/2601.20404); [summary](https://codex.danielvaughan.com/2026/07/27/do-auto-generated-agents-md-files-actually-help-codex-cli/)), with the second figure unverified against its primary paper. Put the verify and dev commands, a one-line package map, and non-lintable rules (no silent fallbacks, prototype breaking changes are fine) in AGENTS.md, import it from CLAUDE.md, and push detail into rule skills and the [stack decisions](stack-decisions.md) file. Do not restate what the linter enforces. Add a UI rule skill, design tokens and a shared `DecisionCard`, since agents "master logic but not taste" ([Addy Osmani](https://addyosmani.com/blog/how-good-is-ai-at-coding-react-really/)).

## Spikes to run first

Six short spikes retire most of the risk before Phase 1 starts. First, a toolchain smoke test (about a day): scaffold the pnpm + Turborepo monorepo on TypeScript 7 with Oxlint/tsgolint, Oxfmt, Vitest 5, Drizzle Kit, Knip and dependency-cruiser, confirm each runs on TS 7 and one `pnpm verify` completes in seconds; deliberately violate a layer rule and check the error text is actionable; wire the Stop hook as a Node script and confirm `pnpm verify` and the hook pass on Windows, macOS and Linux in the CI matrix. Second, the runner on all three systems: the npm-installed runner on Node spawning `claude` (native installer and npm shim on Windows), with cancel and process-tree kill, git worktrees on long Windows paths, and worktree cleanup while a killed process still holds files. Third, adapter conformance: record real Claude Code runs, build golden fixtures and the fake-agent; repeat for `codex exec --json` when Codex is added. Fourth, the API stack: oRPC plus Hono with an SSE `eventIterator`, resume by `Last-Event-ID` against a `run_events` tail, and a fetch-based reader in the browser, with the `@hono/zod-openapi` fallback ready, run behind a reverse proxy to check idle timeouts on long SSE and runner WebSockets. Fifth, dispatch: claiming from the `runs` table with `SKIP LOCKED`, lease, heartbeat, cancel flag and a lost-runner sweep, tested with a killed runner and a sleeping laptop. Sixth, an email-sized vendor task rather than a code spike: ask Anthropic about hosted Claude Code under an engineer's plan and about an open-source local runner spawning the user's installed `claude`, and capture the answer before building the hosted path. The guardrail-loop spike (protected-path hook, CI diff-guard, plan-row-to-test check, then trying to make an agent cheat) moves to the second guardrail stage.

## Conclusion

The stack's surprising property is how little of it is exotic: the risky parts are not the web or API frameworks, where mainstream TypeScript choices are reversible and well covered by agents, but the runner's behaviour on the user's own Windows machine and the terms under which vendors let a subscription login be used. Shipping the runner through npm on Node and keeping the app open source and self-hosted removes code signing, self-update, tenancy and most of the login-handling question, which leaves Windows process control and one confirmation from Anthropic as the irreversible risks to retire first. It also reframes the "AI-agent-friendly" requirement as an enforcement and feedback problem, not a framework-selection problem: a fast single gate, a dev loop agents can start and inspect, and, once they write most of the code, protected tests, mutation testing on core logic and a holdout Verify layer. Those mirror Plangineer's own plan-and-deviation model, so the repo can dogfood the product's philosophy.

The fast-moving components (TS 7, Oxc tooling, Drizzle v1, oRPC 2.0, Vitest 5, TanStack Start) cluster the version risk in the toolchain. The conservative defaults chosen here (Router without Start, Drizzle 0.45, oRPC v1, native Oxlint rules, swappable formatter, Hono OpenAPI fallback) cost little and keep each decision reversible within a day or two, which fits a prototype where breaking changes are acceptable and the first real test is whether engineers find the reviews useful.
